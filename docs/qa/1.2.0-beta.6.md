# 1.2.0-beta.6 verification — 2026-10-25

The three issues confirmed during beta.5 QA were fixed. The scenarios below passed. This is a prerelease; the deferred scenarios are not claims of coverage.

## Changes

- Publish both .NET 8.0.32 x64 and Windows App SDK 2.0.1 with the app. Setup now uses publish output instead of framework-dependent build output.
- Run a side-effect-free `--verify-install` WinUI probe from the staged payload before stopping services or removing an existing installation. A failed or timed-out probe rejects the new installation.
- Keep the close-result message when routine window monitoring hides a locked window. A refused close remains visible as a failure to close, while the lock still applies.
- Assign explicit accessible names to all nine action and icon buttons.

The integration harness compiles the production service and model directly and opens only disposable test windows. It does not read or change WAP PINs, settings, IFEO rules or services. Its cleanup forcibly terminates only children created by the harness; the product close path never forcibly terminates an app.

Windows 10 cleanup left zero protected test apps, no fixture processes, no owned fixture rules, and the WAP service running automatically. Fifteen manual QA scheduled tasks were removed. SMB workload state was preserved. Windows 11 VM testing was stopped when the user directed Windows 11 tests to the local Admin account; its temporary WAP fixture entries/tasks were removed. The separate offline clean-install clone was stopped.

Earlier harness failures were retained in raw evidence: stale selection after saving settings, reading a stale UI element after a native dialog closed, and attempting to inspect elevated installer UI from a lower-integrity runner. These were corrected or independently verified; a successful file-dialog selection and persisted app are recorded separately from the stale-element failure. Installed-app discovery was rechecked after waiting for the actual dialog, excluding background fixture rows.

The isolated VM's product log contains caught GitHub DNS/network errors. These entries do not establish a process crash.

## Deferred / limits

- The user deferred clean-machine installation UI testing. The offline clone was confirmed to lack .NET and the required Windows App Runtime 2.0.1, but no successful clean-machine UI install is claimed. Bundled runtime files, self-contained runtime configuration, runtime probes and existing-machine installs were verified.
- The user was unavailable to supply the local Admin account's existing PIN. Full post-PIN functional UI regression on Windows 11 was therefore deferred; Windows 10 covers those lock paths.
- Real unsaved documents/save-confirm dialogs, different users/integrity levels, browser/window-only protection, packaged-app launch blocking, physical keyboard shortcuts, dedicated WAP reboot/startup, sleep/resume, idle boundary timing and online updater end-to-end remain unverified in this run. Packaged apps are intentionally excluded from graceful process closure.
- No visual-layout pass or exhaustive security audit is claimed. Administrator malware resistance is not guaranteed.

Raw evidence is local and ignored by Git: `build/vm-qa-beta6/Windows10`, `build/qa-windows11-admin`, and build logs. Existing user configuration and PIN hashes are not published.
