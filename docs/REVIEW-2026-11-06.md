# Windows App Protector 코드 검토 보고서

- 작성일: 2026-11-06
- 대상: `codex/1.2.0-beta-1` 브랜치, HEAD `1b8e546` (Release 1.2.0)
- 방법: 소스 정적 분석. 실행 재현은 하지 않았다(이 PC에는 설치·크래시 로그·시작 작업이 없음).

## 0. 요약

보고된 두 증상은 모두 코드에서 원인을 확인했다.

1. **PIN을 입력하지 않으면 종료됨**: 설계 결함이다. PIN 인증 실패·취소·예외가 곧 프로세스 종료로 이어지고, 보호 기능(창 감시·단축키·유휴 잠금)이 이 UI 프로세스 안에만 있어서 보호도 함께 사라진다.
2. **백그라운드에서 먹통**: 원인이 여럿이다. ① 열린 ContentDialog가 남아 있으면 다시 열 때마다 PIN 창이 예외를 내고 즉시 숨겨짐, ② UI 스레드에서 다른 프로세스 창을 동기 호출로 조작함(멈춘 앱이 하나 있으면 같이 멈춤), ③ 작업 스케줄러 기본값 때문에 배터리 전환·72시간 경과 시 프로세스가 종료됨, ④ 앱이 비정상 종료되면 숨긴 브라우저 창이 복구되지 않음.

보안 프로그램으로서 더 심각한 문제도 있다. **PIN 없이 단축키(Ctrl+Shift+U)만으로 전체 해제가 되고**, 사용자 폴더 파일을 지우면 PIN이 초기화된다. 또 "실행할 때 비밀번호를 묻는" My Lockbox 방식이 아니어서 대체품 요건을 충족하지 못한다.

## 1. 증상 ①: 최초 실행 후 PIN 미입력 시 종료

| # | 위치 | 내용 |
|---|---|---|
| 1-1 | `MainWindow.xaml.cs:102-106` | `EnsureWindowAccessAsync(isInitialLaunch: true)`가 `false`면 `ExitApplication()`. 취소 버튼(라벨 "종료"), Esc, 다이얼로그 예외, 내부 예외가 모두 `false`를 반환한다. |
| 1-2 | `MainWindow.xaml.cs:890-893` | 이미 인증 중(`isAuthenticating`)이면 `false` 반환. `ViewModel.InitializeAsync()`(설정 로드, schtasks 실행, IFEO 동기화)가 도는 동안 트레이를 클릭하거나 Ctrl+Alt+W를 누르면 그쪽이 PIN 창을 먼저 띄운다. 그러면 초기 인증은 `false`를 받고 **앱이 종료되는 경쟁 조건**이 생긴다. 로그인 직후 자동 시작될 때 특히 잘 생긴다. |
| 1-3 | `App.xaml.cs:37`, `MainViewModel.cs` `InitializeAsync` → `SyncStartupPreference` | 창을 `Activate()`한 뒤 UI 스레드에서 `schtasks.exe /Create`를 동기 실행(`ReadToEnd`+`WaitForExit`)한다. 그 시간만큼 PIN 창이 늦게 뜨고, 그동안 메인 창이 **PIN 없이 조작 가능한 상태로 노출된다**. |
| 1-4 | 구조 | 브라우저(chrome/msedge/whale 등) 잠금, 유휴 자동 잠금, 단축키는 전부 UI 프로세스의 `DispatcherTimer`에 들어 있다. 서비스는 IFEO만 복구한다. 그래서 UI가 종료되면 **브라우저 잠금과 유휴 잠금이 즉시 무력화된다**. |

**해결 방안**
- "보호 엔진의 수명"과 "관리 화면 접근 인증"을 분리한다. 인증이 실패하거나 취소되면 종료하지 말고 `HideToTray()`로 숨긴다. 종료는 PIN을 인증한 뒤 메뉴에서만 허용한다.
- 시작 순서: 보호 엔진(타이머)과 트레이 → 설정 로드 → 창은 **숨긴 상태로 시작** → 사용자가 열 때만 PIN 확인. 자동 시작(`--background` 인자)일 때는 창이나 PIN 창을 아예 띄우지 않는다.
- `isAuthenticating` 중복 호출은 `false` 대신 진행 중인 인증 Task를 공유(`Task<bool>` 캐시)하도록 바꾼다.
- schtasks 동기화는 매 실행마다 하지 말고 설정을 바꿀 때만, 백그라운드 스레드에서 한다.

| 2-9 | 부재 | 절전·복귀, 세션 잠금(Win+L), 사용자 전환을 처리하지 않는다. | 복귀 후 다시 잠기지 않는다. `GetLastInputInfo` 유휴 시간만으로 판단한다. |

**해결 방안**
- 창 감시는 UI 스레드에서 떼어낸다. `SetWinEventHook(EVENT_OBJECT_SHOW / EVENT_SYSTEM_FOREGROUND)` 이벤트 방식으로 바꾸거나, 최소한 백그라운드 스레드에서 열거하고 `ShowWindowAsync`로 조작한다.
- `AttachThreadInput`은 제거한다. 포그라운드 전환은 `AllowSetForegroundWindow`와 트레이 클릭 시 허용되는 `SetForegroundWindow`로 충분하다.
- 트레이 아이콘은 `RegisterWindowMessage("TaskbarCreated")`를 받았을 때만 다시 추가한다.
- ContentDialog는 하나만 열리도록 관리한다(열린 다이얼로그를 `Hide()`한 뒤 PIN 창 표시). PIN 확인은 메인 창과 분리된 전용 잠금 창으로 하고, **인증 전에는 메인 창을 보여주지 않는다**.
- 시작 작업은 Task Scheduler COM API(또는 XML `/XML`)로 만들고 `DisallowStartIfOnBatteries=false`, `StopIfGoingOnBatteries=false`, `ExecutionTimeLimit=PT0S`, `RestartOnFailure`를 지정한다.
- 숨긴 창 핸들 목록은 파일로 저장해, 다음 실행·서비스·제거 시 복구한다.
- `Global\` Mutex와 `AppInstance.FindOrRegisterForKey`로 단일 인스턴스를 만들고, 두 번째 실행은 기존 인스턴스를 활성화한다.
- `WM_POWERBROADCAST`, `WTSRegisterSessionNotification`에서 즉시 재잠금한다.
- 크래시 로그 외에 일반 진단 로그(타이머 지연, 다이얼로그 실패)를 남긴다.

## 4. 기능 요건 차이 (My Lockbox 대체 관점)

현재 "잠금"은 **실행 자체를 막는 것**이다(IFEO 차단 안내 또는 창 숨김). 잠긴 앱을 쓰려면 WAP를 열고 → PIN → 해제 → 사용 → (유휴 시간이 지나야) 재잠금 순서를 거쳐야 한다. My Lockbox처럼 **보호 앱을 실행할 때 비밀번호를 묻고, 맞으면 바로 실행하고, 앱을 닫으면 다시 잠그는** 흐름이 없다.

권장 구조:
1. IFEO Debugger를 `asInvoker` 경량 런처(`WAP.Gate.exe`)로 지정한다. 런처가 PIN 창을 띄우고, 인증에 성공하면 서비스에 "이 실행 1회 허용"을 요청한다. 서비스가 원래 exe를 IFEO 우회 플래그(`DEBUG_PROCESS` 분리 또는 일시 허용 토큰)로 실행한다.
2. 상태(해제 여부, 해제 만료 시각, 시도 횟수)는 **서비스가 단독으로 소유**한다. UI와 런처는 Named Pipe IPC로 요청만 보낸다. PIN 해시는 ProgramData(관리자·SYSTEM 전용 ACL)에만 두고, 사용자 폴더에는 두지 않는다.
3. 창 숨김 방식(브라우저용)도 서비스가 사용자 세션에 띄우는 감시 에이전트로 옮기고, 에이전트가 죽으면 서비스가 다시 띄운다.

## 5. 기타 운영 이슈

- 인계서는 있다: `docs/HANDOFF-2026-11-03.md`(Codex 작성). 다만 기준 경로가 `C:\Users\Admin\Documents\Codex_Project\...`로 현재 작업 폴더(Google Drive)와 다르다. 인계서는 beta.6 기준인데 이후 `1b8e546`에서 1.2.0 정식판이 나왔다. 인계서에 남은 미검증 항목(재부팅·자동 시작, PIN 이후 전체 UI, 온라인 업데이트)이 검증됐는지 기록이 없다.
- 저장소가 **Google Drive 동기화 폴더 안에** 있다. `.git` 손상 위험이 있다. 수십 MB짜리 `Setup.exe`/`zip`이 버전별로 Git에 커밋돼 있어(50MB 경고) 저장소가 계속 커진다. 릴리스 자산은 GitHub Releases에만 두는 편이 좋다.
- UI(`ProtectionService.cs`)와 서비스(`WindowsAppProtector.Service.cs`)에 IFEO 동기화 코드와 브라우저 목록이 중복돼 있다. 둘이 서로 다른 설정 파일을 기준으로 규칙을 덮어쓸 수 있다. 규칙 쓰기는 서비스 한 곳으로 모아야 한다.
- 자동화된 단위 테스트가 없다. 통합 시험 프로그램 하나만 있다.

| 단계 | 내용 | 규모 |
|---|---|---|

1단계만 해도 보고된 두 증상과 치명 보안 결함은 해소된다. 3단계를 해야 My Lockbox를 대체할 수 있는 수준이 된다.

## 7. 1단계 핫픽스 적용 및 실행 검증 (2026-11-06)

변경 파일: `App.xaml.cs`, `MainWindow.xaml.cs`, `Services/StartupService.cs`, `ViewModels/MainViewModel.cs` (미커밋, 버전 미변경)

검증 방법: Windows 11 개발 PC에서 Release x64 빌드 산출물을 관리자 권한 UI Automation 스크립트로 구동했다. 보호 앱 목록이 빈 시험용 설정을 썼고, 기존 `pin.json`은 시험 동안 따로 보관했다가 해시를 대조해 복원했다.

| 시험 | 결과 |
|---|---|
| 최초 실행 시 PIN 창만 보이고 메인 목록은 숨겨짐 | 통과 |
| PIN 창 "닫기" 후 프로세스 유지·창 숨김 (종료되지 않음) | 통과 |
| 두 번째 실행 시 인스턴스 1개 유지, 기존 창 호출 | 통과 |
| PIN 설정 후 메인 화면 표시, X 클릭 시 트레이로 숨김 | 통과 |
| 숨김 상태에서 Ctrl+Shift+U → PIN 요구, 취소 시 해제 안 됨 | 통과 |
| 5회 오류 → 30초 잠금, 잠금 중에는 올바른 PIN도 거부 | 통과 (첫 실행의 FAIL은 시험 스크립트의 대기 시간 부족, 재시험으로 문구 확인) |
| `--background` 시작: 창 없이 상주(28초 이상), 재실행 시 창과 PIN 표시 | 통과 |
| 시작 작업 XML: 배터리 제한 해제, 시간 제한 PT0S, 우선순위 4, `--background` | 통과 (임시 작업으로 등록 후 삭제, 권한 수준만 LeastPrivilege로 대체) |
| 시험 중 크래시 로그 생성 | 없음 |

미검증: 실제 로그인 시 예약 작업 자동 시작, 노트북 배터리 전환, 보호 앱이 있을 때 IFEO·창 숨김 동작 회귀, 업데이트 대화상자와 PIN 창 충돌(현재 최신 버전이라 업데이트 창이 뜨지 않음), Windows 10.
