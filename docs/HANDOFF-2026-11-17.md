# App PIN Guard 2.0 인수인계서

2026-11-17 KST · 로컬 개발 후보 `2.0.0-alpha.4`

## 현재 상태

2.0의 Win32 실행 PIN, 앱별 정책, 공유 설정 이전 및 세션 에이전트 구현을 로컬 빌드에 포함했다. **다음 작업은 격리 Windows VM에서 1.x → 2.0 업그레이드와 실제 PIN 실행 흐름을 검증하는 것이다.** 제품명은 App PIN Guard로 확정했다. 1.3.1·1.4.0 개선은 2.0에 합쳤다.

- 작업 위치는 `D:\Dev\Windows App Protector`다. `master`의 기준 커밋은 `2866ff8`이며, 2.0 소스와 신규 파일은 미커밋 상태다. 개발 산출물을 재현할 때 HEAD만 체크아웃하면 2.0 변경이 빠진다.
- `dist/installer/Setup.exe`, `dist/releases/1.2.0/Setup.exe`, `dist/releases/1.3.0/Setup.exe`의 기존 미커밋 삭제 상태를 보존한다. 새 빌드는 별도 작업 경로에서 생성한다.
- 마지막 확인 시 공개 안정판은 기존 이름의 1.3.0이었다. alpha.4는 로컬 검증용이다. 공개나 안정판 승격 전 GitHub 상태를 다시 조회한다. [공개 1.3.0 릴리스](https://github.com/droidbin/Windows-App-Protector/releases/tag/v1.3.0)

## 다음 작업 순서

1. **격리 VM 확보.** 로컬 Hyper-V에는 등록된 VM이 없었다. 과거 공유 QA 호스트의 접속은 다른 프로젝트의 자격 증명 사용을 이유로 자동 승인 검토에서 거부됐다. 사용자가 이 작업용으로 지정한 Windows 테스트 환경을 사용하고, 다른 작업이 진행 중인 공유 VM은 건드리지 않는다.
2. **1.x 기준 상태 기록.** Windows 10/11 x64 테스트 VM에서 공개 1.3.0을 설치하고 체크포인트를 만든다. 시험용 PIN·보호 앱·자동 시작을 설정하고 버전, 보호 목록, 서비스 상태를 기록한다. PIN 원문과 해시는 증거에 넣지 않는다.
3. **alpha.4 업그레이드.** 설치 파일 해시를 대조하고 업그레이드한다. 기존 PIN 인증, 보호 목록·예약 작업 보존, 서비스 자동 시작 및 새 표시 이름을 확인한다. 재부팅 후 서비스와 로그인 세션의 에이전트를 각각 확인한다.
4. **실제 PIN 실행과 세션 감시.** Launch Gate를 켜고 시험용 Win32 실행이 IFEO를 거쳐 PIN을 표시하는지 확인한다. 취소·오답은 실행 차단, 정답은 원래 인자와 사용자 권한으로 실행, 종료·허용 시간 만료는 재잠금이 기준이다. 브라우저와 실제 MSIX 앱을 잠근 뒤 관리 UI 종료, 에이전트 강제 종료 후 서비스 재기동, 해제 후 창 복원을 확인한다.
5. **릴리스 판단.** Windows 빌드·후보 해시·항목별 결과를 남긴다. 미검증 상태의 설치 동작을 통과로 기록하지 않는다. 이름을 바꾸거나 복사한 실행 파일에 대한 보호와 서비스 단독 IFEO 쓰기는 남은 설계 항목이다. 서명 제외와 SHA-256 검증 유지 결정은 [차기 버전 로드맵](ROADMAP-NEXT.md)을 따른다.

## Codex 후속 작업 (2026-11-17)

Codex가 사용량 한도로 중단되어 일부를 Claude가 마무리하고 검증했다. 커밋은 하지 않았다.

**변경 내용**
- **서비스 단독 IFEO 쓰기.** UI의 `ProtectionService`는 레지스트리를 쓰지 않고 서비스에 `SyncPolicy` 요청만 보낸다. 서비스 서버는 호출자 실행 파일 경로가 UI인지, 관리자·대화형 세션인지 확인한다. 서비스에 연결할 수 없으면 오류를 표시하며 UI가 IFEO를 직접 쓰는 대체 경로는 없다.
- **빌드 오류 수정.** 공유 파일 `src/LaunchGate/GateProtocol.cs`가 .NET 8(WinUI)에서 `NamedPipeClientStream`의 `PipeAccessRights` 생성자가 없어 컴파일에 실패했다. `NET5_0_OR_GREATER`에서는 `PipeDirection.InOut` 생성자를 쓰고, csc(.NET Framework) 빌드는 기존 생성자를 유지한다.
- **문서·키트.** `docs/DESIGN-rename-bypass.md`(이름 변경·복사 우회 설계 노트, 49줄)와 `tests/VmVerification/`(한국어 README, `Collect-Evidence.ps1`)를 추가했다.

**확인 결과**

| 항목 | 결과 |
|---|---|
| `dotnet build src/WinUI3 -c Release -p:Platform=x64` | 통과 (경고 0, 오류 0) |
| `tests/SettingsMigration` | 통과 |
| csc 컴파일: 서비스, Gate, WindowAgent | 모두 통과 |
| `Collect-Evidence.ps1` 구문 분석 | 오류 0 (실행은 하지 않음) |
| `tests/WindowAgentSmoke` | 이번에는 재실행하지 않음 |

**남은 항목 (VM 필요)**
- 서비스 `SyncPolicy` 경로의 실제 IPC·IFEO 반영, 서비스 제거 시 IFEO 복원, 위 "다음 작업 순서" 1~5번 전체.
- 이전의 Safer 규칙 정리(`CleanupLegacySoftwareRestrictionRules`)는 서비스 쪽 `SaferCodeIdentifiersPath` 처리로 옮겨졌는지 VM에서 확인한다.
- 이름 변경·복사 우회는 설계 노트만 있고 구현하지 않았다.

## 잠금 해제 후 커서 숨김 수정

**원인과 수정**
- 확인된 사실: 저장소 전체에 `ShowCursor`, `SetCursor`, `SetSystemCursor`, `ClipCursor`, `SystemParametersInfo` 호출은 없었다. 반면 세션·전원 알림을 받는 숨은 최상위 메시지 창은 `WNDCLASSEX.hCursor`를 `NULL`로 등록하고 있었고, 별도의 `WM_SETCURSOR` 처리도 없었다. alpha.4에서 이 창에 WTS 세션 알림과 전원 복귀 처리가 연결됐다.
- 실기기 확인이 필요한 가설: 잠금 화면의 보안 데스크톱에서 일반 데스크톱으로 돌아올 때 이 메시지 창의 빈 클래스 커서 때문에 직전의 숨김 커서 상태가 다른 창이 커서를 다시 설정할 때까지 남았다. 대화형 잠금 해제를 이 환경에서 재현할 수 없어 이 인과관계 자체는 코드 검토만으로 확정하지 않았다.
- 수정: 메시지 창 클래스를 시스템 표준 화살표 커서(`IDC_ARROW`)로 등록했다. 원인 확인을 위해 기존 `protection.log`에 `session-unlock`·`power-resume` 시점의 커서 상태(`visible`, `hidden`, `unknown`)만 남긴다. PIN, 앱 경로, 사용자 정보는 기록하지 않는다. PIN 및 잠금 동작은 바꾸지 않았다.

**변경 파일**
- `src/WinUI3/MainWindow.xaml.cs`: 메시지 창의 클래스 커서 지정, 잠금 해제·절전 복귀 커서 상태 진단 추가.
- `docs/HANDOFF-2026-11-17.md`: 원인, 수정 및 검증 결과 기록.

**빌드 및 테스트 결과**
- `dotnet build src/WinUI3/WindowsAppProtector.WinUI.csproj -c Release -p:Platform=x64`: 통과, 경고 0개, 오류 0개.
- `dotnet run --project tests/SettingsMigration/SettingsMigration.csproj -c Release`: 최종 통과. 첫 실행은 동시 저장 시험의 임시 `config.json`을 `File.Replace`하는 중 일시적 `IOException`으로 중단됐으나, 변경 없이 즉시 재실행해 전체 PASS를 확인했다.
- 서비스·Launch Gate·WindowAgent 소스는 변경하지 않았으므로 .NET Framework `csc` 검증 대상이 아니다.

**실제 Windows 세션에서 남은 확인**
- App PIN Guard가 트레이에서 실행 중인 상태와 관리 창이 열린 상태 각각에서 Win+L 후 잠금 해제하고 커서가 즉시 보이는지 확인한다.
- 절전 후 복귀와 다른 사용자로 전환했다가 돌아오는 경우에도 커서가 즉시 보이는지 확인한다.
- 각 시나리오에서 보호 앱 재잠금, 숨김·복원, PIN 요구가 기존대로 유지되는지 확인하고, 문제가 남으면 `%ProgramData%\Windows App Protector\Logs\protection.log`의 해당 `session-unlock` 또는 `power-resume` 줄을 대조한다.
